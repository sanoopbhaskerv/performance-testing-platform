Other traps, all real, all hit at least once:

- Bash working directory **persists between calls**. `cd` into `platform-ui` breaks later commands.
  Always `cd` to the repo root or use absolute paths.
- Single test across the reactor needs `-Dsurefire.failIfNoSpecifiedTests=false`.
- `platform-ui/src/App.css` is **imported by nothing** — `main.tsx` loads only `index.css`.

  `--platform.orchestration.execution-provider=local-jmeter`. Never present a `fake` run's numbers
  as evidence a system performs.

## 2. First: make a synthetic run unmistakable

**Do this before the report work.** A report is precisely the artifact that gets screenshotted and
pasted into tickets, so the marking has to exist before there is a report to mark.

### The problem

The `fake` provider is the default, produces a plausible results file, and the console renders
*"Passed — p95 was 206ms against a ceiling of 750ms"* with **no marker at all**. The only disclosure
is inside `runner-manifest.json`, which someone has to know exists, know to open, and know how to
read. The loudest claim carries the quietest caveat, and the number travels while the caveat does not.

It is worse than it looks: the synthetic samples were deliberately given a zero failure rate so the
demo would not breach the 1% error objective for an unrelated reason. The result is a provider that
*always* produces a green, plausible verdict. A fake that always passes is the most misleading kind.

This also fails the standard the rest of this codebase holds to. Everywhere else a bad state is made
unrepresentable — `RunTransition` makes an unrecorded transition impossible, artifact key prefixes
make a cross-team read unconstructable, `JmxWriter` makes defect D1 structurally impossible. Here the
protection is a sentence in a document, which is the weakest enforcement available, used for the one
thing that fabricates evidence.

### What to build

1. **Carry it on the run, not only in an artifact.** Add `synthetic BOOLEAN NOT NULL DEFAULT false`
   to `test_runs` (Flyway `V5`, alongside `run_metrics`). Set it from the provider that executed the
   run — `ExecutionProvider` should declare whether it generates real load, so this is a property of
   the provider rather than a string comparison on its name. Surface it on `TestRunResponse`, and on
   the report.

2. **Show it in the UI, permanently.** A banner on any run where it is true, and on the report:
   *"No load was generated. These measurements are synthetic and describe nothing."* Not a tooltip,
   not a footnote — it must survive a screenshot.

3. **Show the active provider in the console header.** One line, always visible.

4. **The strong version, and the recommended one: a synthetic run must not produce a green verdict.**
   Report its objectives as `INDETERMINATE` with detail "no load was generated, so nothing could be
   measured". The platform already has that concept and it already means exactly this. The cost is
   that the local demo shows `INDETERMINATE` rather than `Passed`, which is the correct outcome for
   a run that measured nothing — and the `PASS` path is already covered thoroughly by
   `RunAnalysisTest`, so nothing is lost in coverage.

   If (4) is taken, `RunLifecycleEndToEndTest` needs updating: it currently asserts `COMPLETED`, and
   should assert the run reached a terminal state with indeterminate objectives. Its job is wiring,
   not verdict logic.

Be suspicious of the argument that (4) makes the platform less impressive to demonstrate. That is the
argument to distrust most, given what this platform is for.

## 3. Then: reports

**None of this exists today.** Confirmed by grep: no report endpoint, no report UI, no artifact
download. `GET /api/v2/test-runs/{runId}/artifacts` returns *references only* — key, digest, size —
and deliberately no URL.

The data is all there and already stored. Nothing new needs measuring.

### 3a. Artifact download (build first — the report links to it)

`GET /api/v2/test-runs/{runId}/artifacts/{artifactId}/content`

- Authorize per request via `ReadTestRunUseCase` (it already does the team check).
- **Never store or return a pre-signed URL** (CLAUDE.md §17). Time-limited grants minted per
  request; a stored URL is a reference that works until it silently does not.
- Stream from `ArtifactStore.read`, set `Content-Type` and `Content-Disposition` from the stored
  reference, verify the digest before serving.
- 404 for an artifact belonging to another team — same as one that does not exist, so the endpoint
  is not an oracle for which run ids are real.

### 3b. Report endpoint

`GET /api/v2/test-runs/{runId}/report`

CLAUDE.md §19 lists it. Build it as **JSON**, not HTML — the UI renders it, and a server-rendered
HTML blob is what V1 did (`perf-report.html` at the repo root is the V1 artifact).

Assemble from what is already persisted:

| Piece | Source |
|---|---|
| Run, timings, failure code | `TestRunRepository.find` |
| Objective verdicts | `ResultCatalog.objectiveOutcomesFor` |
| Per-operation metrics | **Not persisted yet — see below** |
| Timeline | `TestRunRepository.events` |
| Artifacts | `ResultCatalog.artifactsFor` |
| Plan digest, engine, shard count | `ExecutionPlanRepository.find` |

**The one real gap — DECIDED, do not relitigate.** `NormalizedRunResult` (p50/p90/p95/p99,
throughput, error counts per operation) is computed during analysis and then **thrown away**; only
the objective verdicts are stored.

**Persist it.** Flyway `V5` adds a `run_metrics` table, written by `RunWorkloadService.analyze` in
the same transaction as the objective outcomes. A report that stops working once artifact retention
expires is not a report, and recomputing a large JTL on every read is the wrong cost to pay on the
path a person waits on.

Shape it on `OperationMetrics`, one row per operation plus one for the `*` aggregate:

```
run_metrics(
  id, run_id -> test_runs, operation,          -- '*' for the whole run
  sample_count, error_count, unparsed_count,   -- unparsed stays in the error denominator (D5)
  min_millis, max_millis, mean_millis,
  p50_millis, p90_millis, p95_millis, p99_millis,
  throughput_per_second_milli,                 -- scaled integer, never a double
  shards_expected, shards_reported,            -- an incomplete run can never read as a pass
  measured_from, measured_to, recorded_at,
  UNIQUE (run_id, operation)
)
```

Everything is an integer for the reason the rest of the platform is: these values decide pass or
fail, and a comparison that can differ in the last bit between two reads is not a verdict. Write
through a `ResultCatalog` method (`recordRunMetrics` / `runMetricsFor`), replacing on re-analysis
exactly as `recordObjectiveOutcomes` does — a report showing one operation twice with different
numbers is worse than no report.

Recomputing from `results.jtl` via `engine.parse` + `RunResultReducer` stays available as a
*verification* path, and is worth one test asserting the stored numbers match a recomputation.

### 3c. Report UI

Add to `platform-ui/src/v2/`:

- `api.ts` — add `getReport(runId)` and `artifactContentUrl(runId, artifactId)`. **All V2 access goes
  through this client** (CLAUDE.md §8); do not scatter axios calls into components.
- New `RunReport.tsx`, rendered from the existing run-detail panel in `PerformanceConsole.tsx`.
- Show: verdict summary, per-operation latency table (p50/p90/p95/p99, throughput, error rate),
  the stage profile, and artifact download links.
- Consumer language only (CLAUDE.md §24) — no thread groups, JMX, samplers or Kubernetes.
  An advanced read-only "generated plan" view is permitted and is where the JMX may be shown.
- **If any chart is added, load the `dataviz` skill first.** Do not hand-roll chart colours.

### 3d. Tests to add with it

- Report assembles correctly for a passed run, a breached run, and an `INDETERMINATE` run.
- A report for a run with no analysis yet returns something honest, not a fabricated zero.
- **A report for a synthetic run is marked as such** — the flag from section 2 reaches the report
  payload, not just the run.
- Artifact download refuses another team's artifact with 404.
- Digest verification rejects tampered content.
- Stored `run_metrics` match a recomputation from `results.jtl` via `engine.parse` +
  `RunResultReducer`.

## 4. After reports — Increment 1E

In order:

1. **Kubernetes execution provider** behind `ExecutionProvider`. Job manifest builder, resource and
   security policy, `backoffLimit: 0`, `activeDeadlineSeconds`, persisted Job UID, observe/cancel.
   **Never auto-replay a failed material run** — that is duplicate load on a real system.
2. **S3-compatible `ArtifactStore`.** The port and key layout already match; the filesystem
   implementation cannot serve multiple replicas.
3. **Runner image with `ConcurrencyThreadGroup`**, so load stages stop being stepwise. Write
   `docs/operations/runner-calibration.md` alongside — shard count is still hardcoded to 1 pending
   calibration.
4. **Housekeeping:** delete `BaselineExecutionPlanCompiler` (dead since `EngineDispatchingPlanCompiler`
   replaced it); add the missing tests listed in `HANDOFF.md` §3a.

Not 1E, but worth knowing the shape of: a scenario's `operationId` has no real path, method, headers
or body until importers land in **Increment 2**. The renderer emits `GET /{operationId}` —
deliberately obvious rather than plausible. Reports built now will look thin for that reason, and
that is honest rather than a defect to hide.
